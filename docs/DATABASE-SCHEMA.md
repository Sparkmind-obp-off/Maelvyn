# MAELVYN Database Schema — Initial Domain Model

**Version:** 0.1.0  
**Status:** Proposed schema; migration is a technical baseline, not production data  
**Database:** SQLite / Cloudflare D1

## Design rules

- Use opaque text IDs generated by the application (UUIDv7/UUID); do not expose sequential IDs.
- Store timestamps as UTC ISO-8601 text.
- Store monetary values as integer minor units with a required ISO currency code. For IDR, one rupiah is one unit.
- Scope records to a workspace and, when applicable, a venture.
- Use restrictive foreign keys; archive records instead of deleting them.
- Keep contributions, agreements, and ownership interests separate.
- Keep journal entries append-only after posting; correct with reversals.
- Authentication credentials remain with the identity provider. Store only provider subject mappings.
- Never seed real people, contributions, ownership percentages, bank details, or balances into production.

## Main entities

| Entity | Purpose |
|---|---|
| workspaces | MAELVYN operating boundary |
| people | Internal participant profile, minimal personal data |
| workspace_members | Membership and status |
| ventures | Independent venture/project record |
| venture_members | Scoped role and responsibility |
| agreements | Agreement metadata and execution status |
| contributions | Cash/non-cash contribution classification and evidence |
| ownership_interests | Separately agreed ownership record |
| approval_requests / approval_votes | Approval workflow |
| budgets | Approved budget versions |
| finance_accounts | Venture-level chart of accounts |
| journal_entries / journal_lines | Double-entry accounting records |
| assets | Productive asset register |
| audit_events | Append-only business audit trail |

## Ownership semantics

An ownership row may be `proposed`, `approved`, or `effective`. It must reference an executed agreement to become effective. The database intentionally does not calculate ownership from contribution amounts. Percentages, units, vesting, dilution, and transfer restrictions must be explicit in the governing agreement and recorded only after approval.

## Finance semantics

Journal lines carry debit or credit amounts in one currency. The posting service must validate:
- At least two lines.
- Each line has exactly one positive debit or credit amount.
- Sum of debits equals sum of credits for the entry.
- Accounts belong to the same workspace and venture scope.
- The entry is balanced per currency.
- Only a draft can be posted.
- Posted entries cannot be modified or deleted.

The service should write the posting status and audit event in the same atomic database batch as the journal lines. For D1, use prepared statements and its documented batch API; verify transaction behavior against the current D1 documentation before implementing posting.

The initial SQL migration is at `migrations/0001_initial.sql`. It creates structure only; it contains no real participant, ownership, or financial data.
